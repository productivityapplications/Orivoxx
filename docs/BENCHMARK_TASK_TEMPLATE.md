# Benchmark Task Template

A benchmark task is a versioned specification plus a starting repository and a scoring configuration. Tasks are code, not prose: they are validated at registry construction and tested against at least one compliant and one regressed fixture.

## 1. Identity and versions

Every task declares:

| Field | Rule |
|---|---|
| `id` | lowercase kebab-case, stable forever |
| `version` | semantic version; bump on any spec or starting-repo change |
| `rulesetVersion` | bump when a requirement, check, severity, or bench assignment changes |
| `scoringConfigVersion` | bump when weights, caps, or structural thresholds change |
| `specPath` | `PROJECT_SPEC.md` |
| `difficulty` | `starter`, `intermediate`, or `advanced` |
| `timeLimitSeconds` | hard wall-clock limit for the agent |
| `maxSteps` | model/tool step budget |
| `maxOutputBytes` | bounded captured-output budget |
| `network` | `none` or `model-proxy` |

## 2. Specification format

Use the existing deterministic spec parser. Every requirement must be `Verification: deterministic`; benchmark scoring has no LLM path.

```markdown
### REQ-AUTH-001 — Project access must be owner-scoped
- Severity: critical
- Verification: deterministic
- Description: Every request that reads or mutates a project must verify ownership.
- Checks:
  - type: text_contains
    path: src/app/api/projects/[id]/route.ts
    text: assertProjectOwner
```

Supported check types: `file_exists`, `file_absent`, `text_contains`, `text_not_contains`, `dependency_present`, `dependency_absent`, `source_reference_exists`.

## 3. Bench assignment

Every requirement must be assigned to exactly one scored bench:

- `spec` — did the agent build what the spec asked for?
- `security` — did the agent avoid a declared vulnerable pattern?

Structural maintainability is computed from the static import graph and is not a per-requirement assignment.

## 4. Starting repository

- Include `PROJECT_SPEC.md` with the exact spec text.
- Include only the scaffolding an agent needs: package manifest, data layer, session helper, README.
- Do not include fixture solutions or hidden tests.
- Keep the starting tree under the aggregate limit.

## 5. Fixtures

Ship at least two fixture repositories:

- **compliant** — every deterministic check passes.
- **regressed** — at least one requirement fails, and the failure maps to a named rule.

Fixtures are synthetic and redistributable. They are never executed by the scoring engine.

## 6. Scoring configuration

Use a versioned `ScoringConfig`. The default is:

```text
spec 60% / security 25% / maintainability 15%
critical 8 / high 4 / medium 2 / low 1
critical spec cap 59.9; critical security cap 49.9
```

A task may use a different config only with a new `scoringConfigVersion`.

## 7. Tests before merge

1. Spec parses; all requirements are deterministic.
2. `rulesetVersion` and `scoringConfigVersion` match the manifest.
3. Every requirement has a bench assignment.
4. Compliant fixture passes every requirement.
5. Regressed fixture fails the intended requirements and no others.
6. Repository fingerprints differ between fixtures.
7. The task appears in `listTasks()` with the expected requirement count.

## 8. Files to add

```text
packages/benchmarks/src/tasks/<task>/
  PROJECT_SPEC.md
  starting/...
  fixtures/compliant/...
  fixtures/regressed/...
  generated.ts          # generated by scripts/generate-task-assets.mjs
  index.ts              # manifest + definition + fixture exports
```

Register the task in `packages/benchmarks/src/tasks/index.ts`, run `node packages/benchmarks/scripts/generate-task-assets.mjs`, and run the package tests.
